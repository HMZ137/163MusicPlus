# 性能分析报告 · 设置页卡顿（2026-11-22）

> 项目：163MusicPlus（`app/src/main/java/com/qinghe/music163pro/activity/SettingsPageActivity.java`）
> 现象：设置首页点进任一分类页（外观与显示 / 播放与音质 / 交互与浮层），进入前有可感知的卡顿；**卡顿时长与该页设置项数量正相关**。
> 环境：手表，320×320 级别小屏，Android 8.1（targetSdk 27），debug 构建。

---

## 一、实测数据（logcat，TAG=SettingsPerf）

```
11-22 12:35:09  page=appearance   rows=15  耗时=414ms
11-22 12:35:12  page=playback     rows=14  耗时=386ms
11-22 12:35:16  page=interaction  rows=8   耗时=284ms
11-22 12:35:59  page=appearance   rows=15  耗时=380ms
11-22 12:36:19  page=playback     rows=14  耗时=106ms   ← 背景 Drawable 缓存后复测
```

计时口径：`onCreate` 内从 `prefs` 初始化到三个 `buildXxx()` 全部执行完（主线程同步构建）。

### 数据解读

| 项 | 结论 |
|---|---|
| 每行开销 | 约 **8~10 ms/行**（386ms−284ms ≈ 102ms / 6 行） |
| 固定开销 | 约 **200~250 ms**（8 行的 interaction 页也要 284ms） |
| 缓存收益 | 第二次进 playback 降到 106ms —— 说明 **部分开销是 Jit/冷路径**，同一进程内二次访问明显变快 |

**关键疑点**：interaction 页只有 8 行也要 284ms。行构建本身撑不起这个数字，**大头在固定开销**，即 `onCreate` 里非行构建的部分或 `BaseWatchActivity` 的公共初始化。

## 二、嫌疑点（按可疑程度排序）

### S1｜固定开销 ~250ms：`BaseWatchActivity` 公共初始化（未插桩，最可疑）

每个 Activity 创建都会走：

- `attachBaseContext()` → `UiScale.wrap(newBase)`（改写 densityDpi）
- `onCreate` → `WatchBackButton.attach(this)` + `syncVisibility()`
- `BackGesture` 的 `Window.Callback` 包装（`registerActivityLifecycleCallbacks` 里 `onActivityResumed` 替换 window callback）
- 背景/主题初始化（`ThemeManager.accentColor()` 每行 `rippleBackground()` 都会调；是否每次读 SharedPreferences 未确认）

**插桩建议**：在 `BaseWatchActivity.onCreate` 开头/结尾、`attachBaseContext` 前后、`WatchBackButton.attach` 前后分别打 `SystemClock.uptimeMillis()`，差值直接可见。

### S2｜每行 `MaterialSwitch` 构造（中）

`addSwitchRow` 每行 `new MaterialSwitch(this)`。Material 组件首次构造要解析 Material 主题样式集（attr 解析 + TypedValue 查询），冷路径代价高；同页多个 switch 走已热路径后较便宜。
日志里第二页（14 行）第一次 386ms、第二次 106ms 的巨大差异与此吻合：**首次访问某类控件的冷路径成本**被摊在了行数里。

**可行优化**：换系统 `android.widget.Switch` 对比基准；或把 `MaterialSwitch` 必要的样式在 Application 层预热一次。

### S3｜行视图同步全量构建（中）

一页 15 行 = 15 个 LinearLayout + 30+ TextView + N 个 Switch，全部在 `onCreate` 主线程同步构建。本身不该到百毫秒级，但叠加 S1/S2 后，行数成为放大器（这就是「卡顿与项数成正比」的来源）。

**可行优化**：两阶段构建——首屏 6~7 行同步建，剩余行 `container.postDelayed(..., 30ms)` 分批补。需要把三个 build 方法改成「行生产者」结构，改动量中等。

### S4｜`rippleBackground()` 的 Drawable 构造（已优化）

原实现每行 new 两层 GradientDrawable + 一个 RippleDrawable + ColorStateList。**已改为整页缓存一份，各行 `mutate()` 复用**（`SettingsPageActivity.rippleBackground()`）。复测 playback 降到 106ms，可能已包含此项收益，也可能主要是热路径效应，需再测确认。

### S5｜`ThemeManager.accentColor(this)` 的调用频度（低）

缓存背景后每页只调 1 次，影响已缩小。但如果它内部每次都读 SharedPreferences/解析主题，仍可考虑静态缓存 accent 值。

### S6｜其他待排除项（低）

- `LyricSettings` / `LyricsCopyController` 等工具类的静态初始化块
- `WatchUiUtils` / `UiScale` 首次访问
- debug 构建本身（无 R8/无优化）——**release 对比是必做基线**，debug 下所有数字天然偏大

## 二·补｜另外两个用户感知卡顿点（2026-11-22 追加）

### S7｜主界面右上角「页面菜单」（`btn_more` → `showFunctionsOverlay()`）

- **现象**：主播放页点右上角菜单按钮，浮层弹出前有明显延迟。
- **代码**：`MainActivity.showFunctionsOverlay()` / `showBilibiliFunctionsOverlay(song)`（约 879 行 / 1259 行起）。
- **原因分析**：
  1. 浮层是**纯代码一次性构建**：通用版有 row1~row8（约 15+ 个 `createFuncItem`，每项 = 图标 + 文本 + ripple 背景），全部在点击瞬间同步构建；
  2. 每个项的 label 需要**实时状态查询**：`playerManager.isSleepTimerActive()`、`getPlaybackSpeed()`、收藏状态、均衡器开关等——这些如果触发了服务绑定或跨进程查询会更慢；
  3. B 站歌曲走 `showBilibiliFunctionsOverlay`，同样全量同步构建；
  4. `rippleBackground` 类似的逐项 Drawable 构造（如果 `createFuncItem` 内部同款）。
- **插桩点**：`showFunctionsOverlay()` 首尾计时；`createFuncItem` 每次调用打点（看首项与末项的耗时差，可分离冷路径）。
- **候选优化**：菜单浮层**首次构建后缓存复用**（每次只刷新 label 状态，不重建视图）；或首屏 4 项同步、其余 `postDelayed`。

### S8｜冷启动（MainActivity.onCreate 全链路）

- **现象**：应用冷启动到主界面可交互，体感偏慢。
- **背景事实**：`MusicApp.onCreate()` 本身很轻（deviceId 恢复 + `BackGesture.install`，无 IO 密集操作），**冷启动开销集中在 `MainActivity`**。
- **`MainActivity.onCreate` 已知的工作**（约 4400 行的 Activity）：
  1. `setContentView` inflate 主布局 + ViewPager2 两页构建（歌词页行是逐行动态生成的）；
  2. 背景层（`mainBgLayer`）：若用户设置了自定义图片背景，存在**首次解码大图**的可能；
  3. `MusicPlayerManager` 恢复：上次的播放队列/进度/播放状态回读；
  4. 历史与收藏列表回读、AI 歌词缓存目录检查；
  5. `WatchBackButton` / `BackGesture` / 各浮层预热；
  6. 歌词页构建（如果歌单较长，逐行 inflate 会随队列长度变慢）。
- **插桩点**：`MainActivity.onCreate` 内按段落打点（建议切分为：inflate / pager 构建 / 背景加载 / 播放器恢复 / 历史恢复 / 首帧），配合 `reportFullyDrawn()` 与 `adb shell am start -W` 的 TotalTime 对照。
- **候选优化**：
  1. 背景图**降采样解码**（inSampleSize 按屏幕尺寸算）+ 内存缓存；
  2. 播放器恢复**异步化**（先显示 UI，队列回读放后台，回来再刷 UI）；
  3. 歌词页/播放列表**首屏限量构建**；
  4. `reportFullyDrawn()` 打点便于用 macrobenchmark 跟踪。

## 三、复现与测量方法

```bash
# 1. 清日志
adb logcat -c
# 2. 进设置 → 依次点进 外观/播放/交互
# 3. 抓数据
adb logcat -d | grep SettingsPerf

# 冷启动总时长（不含首帧细节，但适合做优化前后对照）
adb shell am start -W com.qinghe.music163pro/com.qinghe.music163pro.activity.MainActivity
```

进一步插桩的推荐位置（按优先级）：

| 位置 | 想回答的问题 |
|---|---|
| `BaseWatchActivity.onCreate` 首尾 | 固定开销里有多少在基类 |
| `WatchBackButton.attach` 前后 | 返回按钮初始化成本 |
| `BackGesture.onActivityResumed` 前后 | callback 包装成本 |
| `SettingsPageActivity` 每个 `buildXxx` 前后 | 三段构建各自占比 |
| `addSwitchRow` 首次调用前后 | MaterialSwitch 冷路径成本 |
| `MainActivity.onCreate` 分段（inflate/背景/播放器恢复） | 冷启动哪一段最贵 |
| `showFunctionsOverlay` 首尾 + `createFuncItem` 逐项打点 | 页面菜单是冷路径还是全量构建 |
| `MainActivity` 首帧 + `reportFullyDrawn()` | 冷启动到真正可交互的口径 |

## 四、已完成的优化

1. ✅ 行背景 Drawable 缓存（`rippleBackground()` 复用 + mutate）
2. ✅ 标题自适应字号（避免截断，与本问题相关性弱但同页顺带做了）

## 五、未做的候选优化（按预期收益排序）

1. **两阶段构建**：首屏行同步、剩余行 `postDelayed` 分批——直接改善体感（首屏 ~100ms 内出现）
2. **S1 固定开销插桩定位**——若确认在基类，收益是**全应用所有 Activity** 的
3. **MaterialSwitch 预热/替换**——消掉冷路径峰值
4. **release 构建对比**——先确认 debug 数字的水分比例
